# Phase 3 — Multi-Constraint Task

## Overview

This is the fifth and final planned Phase 3 task. It evaluates whether a
model can satisfy **several machine-checkable instruction constraints at
once** on a single free-text response — strictly harder than IFEval-lite
(Phase 1), which checks only one constraint per response. A model that
reliably nails single constraints may still drop one when asked to track
2-3 simultaneously (e.g. hitting an exact paragraph count while also
starting with a specific word and including a specific keyword).

## Data

- **Source:** fully synthetic, generated by
  `scripts/generate_multi_constraint_data.py` (same approach as Phase 1's
  `generate_ifeval_lite_data.py` / `generate_jalali_calendar_data.py`),
  not hand-authored.
- **Sample size:** 80 samples, 20 per category, over 20 Persian topics.
- **Categories:**
  - `length_keyword` — 1 length constraint + 1 keyword constraint
  - `length_position` — 1 length constraint + 1-2 position constraints
  - `keyword_position` — 1-2 keyword constraints + 1 position constraint
  - `triple_combo` — 1 length + 1 keyword + 1 position constraint (hardest tier)

### Constraint vocabulary (reused from IFEval-lite)

All constraint types and their rule-based checkers already exist in
`src/utils/instruction_utils.py` — nothing new was added there:

| Group | Types |
|---|---|
| Length | `sentence_count`, `word_count`, `paragraph_count` |
| Keyword | `must_include`, `must_include_exact_count`, `must_exclude` |
| Position | `must_start_with`, `must_end_with` |

## Why not every combination of constraints is used

Naively picking N random constraints per sample risks an **unsatisfiable
combination** — e.g. "must include X exactly twice" together with "must
exclude X" is a straight contradiction, and stacking two length
constraints (say, an exact sentence count with a high minimum word count)
can be accidentally very hard to hit together. The generator enforces
combinability by construction:

- **At most one Length-group constraint per sample** — stacking two risks
  self-contradiction.
- **Keyword-group constraints only combine on *different* words**, drawn
  from disjoint `REQUIRED_WORDS`/`FORBIDDEN_WORDS` lists, so a
  `must_include` and a `must_exclude` in the same sample can never target
  the same word.
- **Position-group's start-word and end-word are always different** when
  both appear in one sample (and every sample also carries a length
  constraint requiring more than one word, so a single-word response can't
  trivially satisfy both anyway).

This was verified two ways, not just asserted:
1. An automated check across all 80 generated samples confirms zero
   include/exclude word overlaps and zero samples with more than one
   length constraint (`tests/test_prepare_multi_constraint_task.py`).
2. A hand-written response was checked against a real 3-constraint sample
   using the actual `check_constraint` dispatcher and confirmed to pass
   all three simultaneously — proving the combination is genuinely
   answerable, not just free of textual contradiction.

## Pipeline Integration

**New `extra.rule_constraints` key — deliberately not reusing an existing
key:**

- IFEval-lite's `extra.constraint` (singular) holds exactly one constraint
  dict, not a list — doesn't fit this task's shape.
- Persian Controllability's `extra.constraints` (plural) is already wired
  in `runner.py` to a judge-based flow (`PersianControllabilityJudge`) for
  its judge-checkable constraint types (lexical/register/dialect) plus a
  semantic-fidelity score, and populates `controllability_*`-specific
  `ScoredResult` fields. Reusing that key here would incorrectly route
  multi-constraint samples through a judge that isn't built for these
  rule-only types, and would also pull in a `pydantic`-dependent code path
  this task deliberately avoids needing.

`extra.rule_constraints` is a new, independent key carrying the full list
of constraint dicts. `runner.py`'s `score_sample()` gained one additive
`elif sample.extra.get("rule_constraints") is not None:` branch (placed
between the existing IFEval-lite and Persian Controllability branches,
which check different dict keys so there's no ordering-dependent
shadowing): it calls the exact same `check_constraint()` dispatcher
IFEval-lite already uses, once per constraint, and sets
`correctness = 1` **only if every constraint passes** — `0` if even one
fails. Every individual constraint's Persian-language pass/fail reason is
joined into `result.notes` for diagnosability (reusing the existing
generic `notes: Optional[str]` field on `ScoredResult` — no schema change
needed). `persian_stability` rubric is applied to the raw output;
`verifiable_reasoning` is not (there's no gold answer to reason toward).

No other task's code path was touched — the addition is a new `elif`
branch keyed on a key no other task uses.

## Running this task

```bash
# 1. (Re)generate the fully-synthetic raw data (already committed, but
#    reproducible from scratch):
python scripts/generate_multi_constraint_data.py

# 2. Convert into task-ready format:
python scripts/prepare_multi_constraint_task.py \
  --input data/raw_sources/multi_constraint_fa_raw.json \
  --output data/tasks/multi_constraint_fa.jsonl

# 3. Run a candidate model against the task:
python -m src.pipeline.runner \
  --task-file data/tasks/multi_constraint_fa.jsonl \
  --model-name gpt-oss-20b-fa-cot-v1 \
  --output-file data/scored_results/multi_constraint_fa__gpt-oss-20b-fa-cot-v1.jsonl

# 4. Aggregate results across all tasks/models:
python -m src.pipeline.aggregate \
  --results-dir data/scored_results \
  --out report.json
```

## Output fields relevant to this task

In `data/scored_results/*.jsonl`, each row (`ScoredResult`) includes:

- `correctness`: `1` only if the response satisfies **all** constraints in
  the sample, else `0`.
- `notes`: pipe-separated (`" | "`) Persian-language pass/fail reason for
  every individual constraint, in the order they appear in
  `extra.rule_constraints` — lets you see exactly *which* constraint(s)
  the model missed even when the sample as a whole failed.
- `persian_stability_llm_total` (0–8), `code_switch_rate`,
  `persian_script_ratio`.
- `verifiable_reasoning_total`: always `null` for this task (not applied).

`extra.category` (one of the 4 combo categories) and `extra.num_constraints`
in the task-ready jsonl let you break down accuracy by difficulty tier at
analysis time (e.g. `triple_combo` accuracy vs. `length_keyword` accuracy).

## Known limitations

- All-or-nothing `correctness` means a response that satisfies 2 of 3
  constraints scores identically (`0`) to one that satisfies 0 of 3 —
  `notes` preserves the per-constraint detail needed to distinguish "close
  miss" from "ignored the instructions entirely" at analysis time, but the
  headline `correctness` metric alone doesn't.
- Same rule-based-checker tradeoffs as IFEval-lite apply here (e.g.
  sentence/word/paragraph counting relies on `split_sentences` and simple
  whitespace/blank-line heuristics, which can misfire on unusual
  formatting the model might produce).
- The dataset is synthetic (topics + constraint templates), not drawn from
  real user instructions — it tests constraint-tracking ability in a
  controlled way, not naturalistic multi-part instruction-following.
- Only 20 topics are used (reused instruction-generation style from
  Phase 1's IFEval-lite, but a smaller topic pool); broader topic
  diversity could be added later without any pipeline changes.
